# Chapitre 7 — « Le squash n'a rien réglé : les migrations fantômes sont revenues »

*Phase 5 — Module IA, fichiers & tableau de bord · 13 août 2026*

---

## 1. Le contexte

Au chapitre 4, j'avais vécu la grande lessive : 7 migrations
chaotiques — des doublons (`add_auth_refresh_tokens` en double, deux
`add_ai_module`), une migration de 20 Ko qui dupliquait tout, et une
base dev vidée silencieusement par les tests. La conclusion de ce
chapitre, c'était le **squash** : sauvegarde de l'historique dans
`alembic/versions_backup_avant_squash/`, puis une seule migration
initiale propre, `0d26806ad448_initial_full_schema.py` (633 lignes,
32 tables, `down_revision = None`). Une base fraîche pouvait se
reconstruire en une seule commande. Je m'étais dit : *« Voilà, le
passé est enterré. On repart propre. »*

La phase 5, c'était la suite logique : le **module IA** (templates de
prompts versionnés, suggestions, feedback), les **évaluations
pondérées**, le **module fichiers** (upload vers MinIO), et le
**tableau de bord** — les compteurs du club, le radar des 4 piliers
par joueur, les synthèses et l'export PDF. La mécanique était
rodée : je modifiais mes modèles, je lançais `alembic revision
--autogenerate`, j'appliquais, je testais.

Sauf que l'historique, lui, n'avait pas dit son dernier mot.

## 2. Le symptôme / le défi

Dans les heures qui ont suivi le squash, j'ai généré **cinq
migrations** pour les nouveaux modules. Le résultat, lu
froidement, donne froid dans le dos :

```
b3ea619cf3d0_add_training_and_planning.py       → upgrade() : pass
fbcb327cba70_add_evaluations_and_weighting.py   → upgrade() : pass
dbd57c83f186_add_ai_module.py                   → upgrade() : pass
97c8bf6a4e60_add_ai_module.py                   → upgrade() : pass
b806a273afbe_add_uploaded_files.py              → upgrade() : op.create_table('uploaded_files', ...)
```

Quatre migrations sur cinq sont **vides**. Des fantômes. Et le
comble : `add_ai_module` est apparu **deux fois de suite**
(`dbd57c83f186`, puis `97c8bf6a4e60` qui s'enchaîne sur lui) — le
même doublon qui existait déjà dans l'historique que je venais
d'enterrer sous `versions_backup_avant_squash/`.

Le pire, c'est la phrase dans la docstring de ces fantômes :

```python
def upgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    pass
```

`pass`. Rien. Alembic ne voyait **aucune différence** entre mes
modèles et la base. J'avais squashé sept migrations chaotiques pour
me retrouver, quatre heures plus tard, avec une chaîne de six
migrations — dont quatre qui ne font rien. Le ménage n'avait servi à
rien.

## 3. Où je cherchais

Mon premier réflexe a été de croire que le problème venait de la
**base** : « Elle n'est pas à jour, c'est pour ça qu'autogenerate ne
voit rien. » J'ai relancé `alembic upgrade head`, re-vérifié
`alembic_version`, réessayé. Rien.

Mon deuxième réflexe, le plus naturel : « C'est un coup de malchance,
je régénère. » C'est exactement ce qui a produit les doublons. Quand
une génération sort vide, on la refait — et si elle ressort vide, on
la refait encore, parfois avec un autre nom (`add_ai_module` →
`add_ai_module`). Résultat : deux migrations fantômes au lieu d'une.
La régénération, c'était le piège, pas la solution.

Et mon troisième réflexe, le plus trompeur : « Le squash a dû tout
réparer, c'est forcément un cas isolé. » Je regardais la migration
`0d26806ad448` — propre, complète, magnifique — et je me disais que
le problème était réglé. **C'était faux.** Le squash avait nettoyé
l'*historique*… mais pas la *machine* qui fabriquait l'historique.

## 4. Où était le problème réellement

La preuve était sous mes yeux, dans `alembic/env.py` — le fichier
que je n'avais presque pas touché pendant le squash.

Alembic `--autogenerate` ne détecte que les modèles **importés** dans
`env.py` : c'est lui qui peuple `Base.metadata`, et c'est ce
metadata qu'Alembic compare à la base. Au moment où j'ai généré les
migrations post-squash, `env.py` n'importait pas les modèles
`training`, `planning`, `evaluations` et `ai`. Donc `Base.metadata`
ne les connaissait pas. Donc autogenerate ne voyait aucune table à
créer. Donc `pass`.

La preuve la plus élégante, c'est la seule migration non vide :
`b806a273afbe_add_uploaded_files.py` crée vraiment la table
`uploaded_files` (avec ses index, ses clés étrangères vers `clubs`
et `users`). Pourquoi celle-là est-elle réelle ? Parce que
`app.files.models` — le modèle `UploadedFile` — était, lui, importé
dans `env.py`. La machine n'était pas cassée : elle était
**aveugle**, et elle ne voyait que les modèles qu'on lui présentait.

Le squash n'avait donc rien réglé du tout : il avait remplacé sept
mauvaises migrations par une bonne… puis la machine avait
immédiatement recommencé à produire les mêmes erreurs. J'avais
nettoyé le sol sans fermer le robinet.

## 5. Comment on l'a résolu

1. **Compléter les imports dans `alembic/env.py`.** Tous les
   modèles, sans exception : `User`, `Club`, `Season`, `Team`, les
   rôles et permissions, `Player`, `PhysicalProfile`, `MedicalRecord`,
   les matchs et formations, `RefreshToken`, les modèles IA
   (`AiTemplate`, `AiSuggestion`, `AiFeedback`), `TrainingSession`,
   `TrainingEvaluation`, `WorkPlan`, `Evaluation`,
   `WeightingMatrix`, `WeightingSnapshot`, et `UploadedFile`. Une
   ligne par famille, avec `# noqa: F401` pour dire à mon linter :
   « oui, je sais, c'est importé pour ses effets de bord, et c'est
   voulu. »

2. **Vérifier la machine, pas le résultat.** Le test qui change
   tout : lancer `alembic revision --autogenerate` **à blanc** après
   le fix. Si la migration générée contient du vrai contenu (ou
   « rien à faire » honnête), la machine voit. Si elle sort `pass`,
   c'est que quelque chose manque encore dans `env.py`. On ne génère
   plus jamais une migration sans ce test.

3. **Rejouer le cycle complet sur base fraîche.** `alembic upgrade
   head` depuis zéro : la chaîne squash → fantômes (inoffensifs, ils
   ne font rien) → `uploaded_files` s'applique sans erreur, et la
   base finale contient toutes les tables attendues.

4. **Terminer le travail métier et tout verrouiller par des tests.**
   Le tableau de bord a pris forme dans `app/dashboard/service.py` :
   l'overview (compteurs de joueurs, matchs, entraînements, dernier
   match avec score), le **radar des 4 piliers** — avec une règle
   métier stricte, écrite en toutes lettres dans le code : *seules
   les évaluations validées par le coach sont agrégées* — et les
   exports PDF. `tests/test_dashboard.py` est venu couvrir tout ça
   (« Tests Phase 7 : tableau de bord, synthèse et export PDF »).

Résultat : **47 tests verts**, aucun échec au cache pytest, et le
projet entier est parti dans un commit unique et propre — « Analystaff
backend V2 — API FastAPI complète (47 tests verts) » — avec la
migration initiale squashée dedans. L'ancien historique, lui, dort
toujours dans `versions_backup_avant_squash/`, comme une pièce à
conviction.

## 6. L'enseignement

> **Squasher l'historique, c'est effacer les symptômes du passé —
> pas réparer la machine qui les a produits.**

Trois réflexes à garder :

1. **Avant de générer une migration, vérifie que `env.py` importe
   TOUS tes modèles.** `--autogenerate` est aveugle à tout ce qui
   n'est pas dans `Base.metadata`. Une migration qui sort avec
   `pass` n'est pas un succès : c'est une alarme. « Rien à migrer »
   signifie « la machine ne voit rien », pas « tout va bien ».

2. **Ne régénère jamais une migration vide sans chercher la cause.**
   La régénération à l'identique, c'est le chemin direct vers les
   doublons (`add_ai_module` deux fois). Quand une génération sort
   vide, la question n'est pas « je relance ? » mais « qu'est-ce
   qu'Alembic ne voit pas ? ».

3. **Après un squash, refais un cycle complet de vérification.**
   Base fraîche → `upgrade head` → autogenerate à blanc → comparer.
   Un squash n'est pas une fin, c'est un point de contrôle. Et garde
   toujours l'ancien historique (`versions_backup_avant_squash`) :
   c'est lui qui m'a permis de reconstituer la vérité quand tout
   semblait propre.

Bonus — la leçon la plus profonde : **on ne répare pas un processus
en nettoyant sa sortie.** Sept migrations chaotiques n'étaient pas un
problème de migrations : c'était un problème d'`env.py`, invisible
derrière le mot « squash ». Chaque fois que tu es tenté de « tout
nettoyer », demande-toi d'abord ce qui a sali, et répare ça — sinon
le désordre reviendra, avec un joli nom de fichier.

---

*Un squash efface le passé. Il n'empêche pas le présent de recommencer.*
