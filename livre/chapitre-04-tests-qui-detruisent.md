# Chapitre 4 — « Les tests passent… mais ma base a disparu »

*Phase 4 — Module IA, matchs & planification · 11 août 2026*

---

## 1. Le contexte

La phase 3 s'était terminée en beauté : **19 tests verts**. J'avais
appris la leçon des tests dans le conteneur, des images obsolètes et des
versions de bibliothèques. Je me sentais confiant.

La phase 4, c'était le gros morceau : le **module IA** (templates de
prompts versionnés, suggestions, feedback), les **matchs** (composition,
plateau tactique, remplacements), les **entraînements**, la
**planification**, les **évaluations**. Tout le cœur métier d'Analystaff.

J'avais une séquence en tête : générer la migration IA → l'appliquer →
seeder les templates → vérifier → lancer les tests. Cinq commandes. Ça
semblait simple.

## 2. Le symptôme

Premier indice : la migration que je générais pour le module IA était…
**vide**.

```python
def upgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    pass
```

`pass`. Rien. Alembic n'avait rien détecté à migrer. Pourtant mes
modèles IA existaient (`ai_templates`, `ai_suggestions`, `ai_feedback`).

Deuxième indice, plus inquiétant : le backend **crashait au démarrage**.

```
ModuleNotFoundError: No module named 'app.roles.schemas'
```

Un fichier `schemas.py` manquant dans le module `roles`, alors que
`router.py` et `staff_service.py` l'importaient.

Et le troisième indice, le plus sournois : **la base de données ne
contenait plus qu'une seule table**. `alembic_version`. Les 17 tables du
schéma avaient disparu. Sans crier gare.

## 3. Où je cherchais

Mon premier réflexe : ma migration. « Elle est vide, c'est elle le
problème. » J'ai passé du temps à la régénérer, à la comparer, à la
relancer. Rien.

Mon deuxième réflexe : le crash backend. « C'est le fichier schemas.py
manquant. » Vrai — mais ce n'était qu'un symptôme de plus, pas la cause
des tables disparues.

Le vrai mystère, c'était la base. Une base de données ne se vide pas
toute seule. Qui avait bien pu supprimer les 17 tables ? Personne ne se
souvient d'avoir lancé un `DROP TABLE`.

Et pourtant : **les tests passaient.** 19 sur 19. Comment pouvait-on
avoir une base vide et des tests verts ?

## 4. Où était le problème réellement

Trois problèmes, encore une fois empilés — mais cette fois, le pire
était invisible.

### Problème n°1 — Les tests détruisaient la base dev (le tueur silencieux)

Le `conftest.py` des tests contenait cette ligne :

```python
os.environ.setdefault("DATABASE_URL", "...@db:5432/analystaff_test")
```

`setdefault` = « ne définit la variable QUE si elle n'existe pas déjà ».
Or, dans le conteneur Docker, `DATABASE_URL` **existait déjà** — pointé
par docker-compose vers la base **dev** (`analystaff`), pas vers la base
de test (`analystaff_test`).

Résultat : `setdefault` ne faisait **rien**. Les tests utilisaient la
base **de développement**. Et comme le conftest commence par
`drop_all` (nettoyage) et finit par `drop_all` (ménage), **chaque run de
pytest supprimait silencieusement toutes les tables de la base dev**.

C'est pour ça que les tests passaient : ils créaient les tables
eux-mêmes au début de la session, les utilisaient, puis les détruisaient.
La base dev n'était qu'un terrain de jeu jetable — sans que personne ne
le sache.

### Problème n°2 — La migration IA était vide (l'import manquant)

Alembic `--autogenerate` ne détecte que les modèles **importés** dans
`alembic/env.py`. Mes modèles IA n'y étaient pas → `Base.metadata` ne
les connaissait pas → la migration générée ne contenait que `pass`.

Et comme la base dev était déjà vidée par les tests, l'autogenerate
comparait les modèles à une base **vide** → il voulait recréer **tout**
le schéma (19 tables en double) au lieu d'ajouter juste les tables IA.
Une migration de 20 Ko qui dupliquait tout, sans les tables
training/planning/evaluations pourtant définies dans les modèles.

### Problème n°3 — Le router matches importé mais jamais monté

Une fois la base reconstruite et les migrations propres, il restait 5
tests en échec avec des **404**. Les endpoints `/matches/*` répondaient
« introuvable ».

Le router `matches` était **importé** dans `main.py`… mais jamais
branché avec `include_router`. Importé ≠ monté. Une ligne manquante, et
toute une API muette.

## 5. Comment on l'a résolu

1. **Conftest : écrasement forcé.** Remplacer `setdefault` par une
   affectation directe :
   ```python
   os.environ["DATABASE_URL"] = "...@db:5432/analystaff_test"
   ```
   Les tests utilisent **toujours** la base de test, jamais la base dev.
   Vérification : 33 tables en base avant pytest… et **33 après**. La
   base dev est enfin protégée.

2. **Env.py : les imports manquants.** Ajouter les modèles IA,
   training, planning, evaluations dans `alembic/env.py`. L'autogenerate
   voit enfin tout le schéma.

3. **Squash des migrations.** Les 7 migrations étaient un embouteillage
   (2× toutes les tables, 1 vide, des noms trompeurs). Sauvegarde de
   l'historique, puis **une seule migration initiale propre**
   (`0d26806ad448`, 32 tables, `down_revision = None`). Une base fraîche
   peut se reconstruire d'un coup.

4. **Main.py : le router manquant.** Ajouter
   `app.include_router(matches_router, ...)` — et nettoyer au passage
   les doublons (health monté 3 fois, auth 2 fois).

Résultat : **24 tests verts** (19 + 5 matchs), base dev intacte, 9
templates IA en base, API saine.

## 6. L'enseignement

> **Les tests qui passent ne prouvent pas que tout va bien. Ils prouvent
> seulement que le code testé fonctionne — pas que la base qu'ils
> détruisent au passage est surveillée.**

Trois réflexes à garder :

1. **Méfie-toi de `setdefault` dans un conteneur.** Si la variable
   d'environnement existe déjà (docker-compose la définit), `setdefault`
   ne fait rien — silencieusement. Quand tu veux FORCER une valeur,
   affecte-la directement (`os.environ["X"] = ...`). Et vérifie toujours
   **quelle base** les tests utilisent réellement, pas celle que tu
   crois.

2. **Après les tests, vérifie l'état du monde réel.** Le test ultime
   d'un environnement sain : compter les tables AVANT pytest, compter
   APRÈS. Si ça diffère, quelque chose détruit ta base. Un test vert
   n'est pas un feu vert pour l'intégrité des données.

3. **`import` ≠ `include_router`.** Importer un module ne le branche
   pas. Un router importé sans `include_router`, c'est une API muette
   qui répond 404 à tout. Après chaque nouveau module : vérifie qu'il
   est monté, pas juste importé.

Bonus — la leçon la plus profonde : **le bug le plus dangereux est
celui qui ne fait échouer aucun test.** La base dev se vidait à chaque
run, et tout le monde voyait 19 tests verts. La santé d'un système ne se
mesure pas qu'à ses tests : elle se mesure aussi à ce qui reste debout
après.

---

*Un test vert n'est pas une preuve d'innocence. C'est une preuve de
non-culpabilité — pour le code testé, pas pour le reste.*
